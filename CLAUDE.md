# CLAUDE.md — Maps Plus

Maps Plus is an open-source Chrome extension (Manifest V3) that adds power-user features to Google Maps on the web (`https://www.google.com/maps/*`). It's built as a set of independent **features** that users can turn on and off in the options page.

Current features:

1. **Pano Date Resolver**: adds a "Resolve date" button next to the Street View "Image capture: <Month Year>" label. It finds the capture time to within about 2 seconds.
2. **Saved Places Lasso**: adds a map control. The user drags a circle (or draws a freehand lasso) over the map to select their saved places (Starred, Want to go, Favourites, custom lists). This opens a panel listing every selected place with a photo, name, category, and address. The list can be exported.

## Non-negotiable principles

- **Privacy first.** No analytics, telemetry, crash reporting, or remote servers run by us. The extension only talks to Google domains the user is already using. User data stays in the browser (`chrome.storage.local`) unless the user explicitly exports it.
- **Minimal permissions.** Don't add new `permissions` or `host_permissions` to the manifest without explaining why in the PR or commit message (and in the README permissions table). Ask before adding `<all_urls>`, `tabs`, `cookies`, `webRequest`, `scripting`, or `downloads`. Avoid them if possible.
- **No secrets in the repo.** Never hard-code API keys. If the user wants optional Google Places API features, they paste their own key into the options page. Store it in `chrome.storage.local` and never log it.
- **Be polite to Google.** Only run network work when the user takes an action (no background crawling). Rate-limit requests (default max 4 at a time, at least 150 ms apart). Cache results. Back off when you get a 429 or 5xx response. Prefer reading data the page has already loaded over making new requests. Background requests use `credentials: 'omit'`.
- **Licensing.** The project is MIT-licensed. Don't copy code from repos without a compatible license. In particular, `itisem/pano-date-resolver` has **no license file**. The technique was written from scratch (see Feature 1); the author is credited in the README and in code comments. If the author later adds a compatible license, the code can be reused directly.
- **Never use `innerHTML` with data from Google or from users.** Build DOM nodes or use `textContent` (`h()` in `shared/dom.ts`). Place names and notes are untrusted input (XSS risk), and that includes exported HTML (escape everything; images only as validated `data:` URLs). ESLint bans `innerHTML`/`outerHTML`/`insertAdjacentHTML`.

## Tech stack

- TypeScript (strict mode, `noUncheckedIndexedAccess`), [WXT](https://wxt.dev) 0.21 for the extension build (MV3, hot reload, multiple entry points). `srcDir` is `src/`; `@/` is an alias for `src/`.
- UI inside Maps: plain DOM inside a **Shadow DOM** root, so Google's CSS and ours don't collide. No framework in content scripts. The options page is plain DOM too.
- Tests: Vitest (unit, `tests/*.test.ts`), opt-in live tests (`tests/live`, `LIVE=1`), Playwright with the unpacked extension (`tests/e2e`, hits live Google Maps, never run in CI).
- Lint/format: ESLint (flat config) and Prettier.
- Exports are generated by hand (CSV, GeoJSON, KML, HTML). DOCX isn't built. Add `docx` only if asked.

## Architecture rules

- Each feature implements:
  ```ts
  interface Feature {
    id: string;
    name: string;
    description: string;
    defaultEnabled: boolean;
    mount(ctx: FeatureContext): void | Promise<void>;
    unmount(): void;
  }
  ```
  `maps.content.ts` mounts the enabled features and remounts them when settings change. Features must not import from each other. Shared code goes in `src/shared`. (The background worker may import a feature's pure, DOM-free modules, e.g. `pano-date/protobuf.ts`, and so may the MAIN-world script for `saved-lasso/data-source.ts`.)
- **Google Maps is a single-page app.** The URL changes without the page reloading, and the DOM gets re-rendered all the time. `shared/spa-watch.ts` provides one shared, throttled `MutationObserver` (one run per 400 ms at most) and a URL-change hook. The isolated world can't see the page's own `history.pushState` calls, so the MAIN-world script patches `pushState`/`replaceState` and fires a `maps-plus:locationchange` event on `window`. `popstate` and a 1 s poll act as fallbacks. Every UI injection must be safe to run repeatedly, without duplicating elements or causing mutation loops (mutations inside `[data-maps-plus]` hosts are ignored).
- **Selectors:** Google's class names are scrambled and change often. Find elements by stable signals first: `aria-label`, `role`, `jsaction`, `data-*` attributes, then visible text. Keep every selector in `shared/maps-dom.ts` with a comment saying when it was last checked. When a selector fails, fall back gracefully (for example, a floating button) instead of breaking.
- **Network:** content scripts send typed messages to the background worker, which makes the request. That avoids CORS problems and keeps rate limiting in one place. The router rejects messages from other extensions and malformed requests.
- **Trust boundaries:** anything from the MAIN world (`isBridgeMessage`: same window, same origin, channel name, shape), from storage, or from imported files goes through `sanitizePlace()` before use.
- **i18n:** Maps text is localised. Text matchers (for example "Image capture") need a table for each language in `shared/i18n.ts`, falling back to structural detection. Only English is verified so far.

## Verified facts about live Google Maps (keep this current)

Checked 2026-11-13, en-US, 1400×900, with Playwright plus software WebGL:

- **Map container:** there is no `#scene`. The vector map is an _oversized_ `<canvas>` (a pan buffer, e.g. 1792×1280 at −246,−255) inside a zero-size wrapper inside a full-window container. The URL `@lat,lng` is the centre of that **full-window container**, not of the area to the right of the nav rail or side panel. With the Eiffel Tower at the URL centre, it rendered at window centre. `findMapCanvas()` walks up from the largest canvas to the first on-screen ancestor at least 200 px in size.
- **Projection:** verified at zoom 16. Selection rings land on the Eiffel Tower and the Trocadéro. Zooms 3, 10, and 18 still need the manual check from the checklist.
- **Map controls:** zoom buttons have `aria-label="Zoom in"/"Zoom out"` and `jsaction` containing `zoom.onZoomInClick` (hidden minimap duplicates also exist). "Show Your Location" sits directly above them. Our control stacks above that column.
- **Nav rail "Saved":** visible text "Saved", no `aria-label`.
- **`role="main"`:** absent on a bare map view. It only appears when a side panel is open.
- **Street View in headless Chromium:** the pano doesn't render (no imagery message) and the "Image capture" label is absent, so the floating fallback is used. The inline placement still needs a manual check in real Chrome.
- **Street View thumbnails** (`streetviewpixels-pa…/v1/thumbnail`, `/v1/tile`, `geo0.ggpht.com/cbk`, `cbk0.google.com/cbk`): all return **403** without a signed-in session. So there's no keyless photo fallback; the UI uses a placeholder.

## Feature 1 — Pano Date Resolver

**Credit:** technique by emily / itisem (https://pano-date.emily.bz, https://github.com/itisem/pano-date-resolver). Reimplemented, not copied (see Licensing).

**How it works:**

1. Parse the current URL to get `lat`, `lng`, and the pano ID if there is one. Supported formats:
   - `/maps/@LAT,LNG,3a,FOVy,HEADINGh,PITCHt/data=...!1s<PANOID>!2e0...`
   - `/maps/@?api=1&map_action=pano&pano=...&viewpoint=LAT,LNG`
   - `/maps?...&layer=c&cbll=LAT,LNG`
     Only official panos are supported (22-character IDs). User-uploaded photospheres show a clear "not supported" message.
2. POST to `https://maps.googleapis.com/$rpc/google.internal.maps.mapsjs.v1.MapsJsInternalService/SingleImageSearch` with `Content-Type: application/json+protobuf`. The body is a positional JSON array (field N at index N−1). **Verified layout** (see `protobuf.ts` and the fixture tests):
   ```
   [ ["apiv3"],                                   // 1 context.productId
     [[null,null,LAT,LNG], 30],                   // 2 location {center LatLng(3,4), radius}
     [FILTER?, …, [2], null, [[[2,true,2]]]],     // 3 queryOptions: 1 filterOptions, 9 ranking CLOSEST, 11 renderStrategy OFFICIAL/tiled/OFFICIAL_FORMAT
     [[2,6]],                                     // 4 components INCLUDE_DESCRIPTION, INCLUDE_LINKED_PANORAMAS
     [2, PANOID] ]                                // 5 imageKey (optional)
   FILTER = [null ×10, [startSeconds, endSeconds]] // filterOptions.11 photoAge
   ```
   Response: `[[0], metadata]` on success, `[[5,"generic","Search returned no images."]]` when empty. Capture month is at `metadata[6][7] = [year, month]`, the pano ID at `metadata[1][1]`, and the pano's coordinates at `metadata[5][0][1][0][2..3]`.
3. Binary-search from 2 days before the start of the month to 2 days after its end (UTC). Search by location (the pano's own coordinates from step 2) without the pano ID, with `photoAge` set to the lower half. If imagery is found, keep that half. Otherwise keep the other half. Stop when the range is 2 seconds or less (21 halvings, 22 requests in total). Progress shows on the button ("Resolving… 12/21").

**UI:** a small pill-shaped button right after the "Image capture" label. If that label isn't found, a floating button appears in the bottom-left. On success it shows the time in the user's local time zone, with a tooltip containing UTC, "±N s", and the photo location's local time from the bundled offline `tz-lookup` (CC0). Clicking the result copies it. Results for a specific pano ID are cached for 30 days.

**Limits explained in the UI tooltip:** it usually works only for the most recent imagery at a location, and it can break if Google changes its internal service.

## Feature 2 — Saved Places Lasso

**User flow:**

1. A map control button ("Select saved places") appears above Google's my-location and zoom column. It's hidden in Street View.
2. Clicking it turns on selection mode: a transparent canvas covers the map area, minus the side panel when one is open. Dragging draws a **circle** (center + radius) by default. Holding Shift, or choosing the mode toggle, switches to a **freehand lasso**. Esc cancels.
3. The selected saved places get highlight rings. A side panel lists each place with a thumbnail, name, category/type, address, which saved list(s) it's in, the distance from the circle's centre, and the user's note if there is one. Users can remove individual rows, sort by distance/name/list, and filter by list.
4. Export buttons: **CSV**, **GeoJSON**, **KML**, **HTML report** (self-contained, CSP `default-src 'none'`, images embedded as data URLs, print-friendly). DOCX is not built.

**Getting saved-place data (in this order):**

1. **Read what the page already loaded (preferred).** `maps-main-world.content.ts` runs in the MAIN world at `document_start`. It wraps `fetch` and `XMLHttpRequest.open`, and for same-origin responses whose path matches `/maps/preview/entitylist/getlist` it strips `)]}'`, runs `parseGetlist()`, and posts the place records over `BRIDGE_CHANNEL`. It never makes requests of its own. Captured places are merged into `chrome.storage.local`.
   - ⚠️ **The getlist response layout is UNVERIFIED.** It needs a signed-in session. The parser is structural (coordinate tuple → location block → place record → list record) so that it survives index changes. The expected concrete paths are documented in `data-source.ts`. **Next step:** open a saved list in DevTools, confirm the endpoint and the paths, add an anonymised fixture to `tests/fixtures/`, and pin the paths. If the endpoint differs, add it to `WATCHED` in the MAIN-world script.
   - The empty state offers "Open my Saved lists" (clicks the nav rail's Saved item) and Takeout import.
2. **Import a file (fallback).** Google Takeout `Saved Places.json` (GeoJSON; both the old `Title/Location/Geo Coordinates` and the new `location.name/address` property layouts are handled), plus per-list CSVs (`Title, Note, URL, …`; the list name comes from the file name). Coordinates come from `!3d…!4d…`, `@lat,lng`, or `query=` in the URL. Rows without coordinates are counted and reported, not guessed. Resolving them from the place page is a TODO and must be rate-limited if built.
3. **Never** ask for the user's Google password or cookies. Never make authenticated requests from another origin.

**Turning screen selection into places:**

- Read the map view from the URL `@LAT,LNG,ZOOMz` (zoom can be fractional) once it has stopped changing for 300 ms. Satellite and 3D URLs use `,METERSm`. `zoomFromMeters()` treats the value as the ground height of the canvas. That's **unverified**, so the UI says "approximate".
- Web Mercator: `worldSize = 256 * 2^zoom`, `x = (lng + 180) / 360 * worldSize`, `y = (0.5 - ln((1 + sin φ) / (1 − sin φ)) / (4π)) * worldSize`. Take the difference from the projected centre and add the container centre. Wrap x by ±worldSize to the nearest copy (antimeridian).
- Test against the shape: point-in-circle, or ray-casting point-in-polygon for the lasso, which is simplified first with Ramer–Douglas–Peucker (iterative).
- A tilted view (`,…t` in the URL) is refused with "Please switch to a flat, untilted map to select". Zoom below 2 is refused too.

**Details for each place (photo, category, address):**

- Data already present in the intercepted records comes first.
- If the user entered their own Places API (New) key: `places:searchText` (name, location bias 150 m, 1 result) plus photo media (`skipHttpRedirect=true`), through the background worker, rate-limited, cached for 30 days by place key. Failures aren't cached.
- With no key, no lookup is made and the UI shows a placeholder (see the thumbnail 403s above).
- Rows are hydrated lazily (IntersectionObserver), so only rows the user scrolls to trigger lookups.
- In HTML exports, images are downloaded by the background worker (only from `*.googleusercontent.com`), downscaled to at most 400 px wide as JPEG at quality 0.8, and embedded as data URLs.

**Export details:**

- CSV: UTF-8 with BOM, CRLF. Columns: name, category, address, lat, lng, lists, note, google_maps_url, photo_url. Cells starting with `= + - @` get a `'` prefix (formula injection).
- GeoJSON: a FeatureCollection with the same properties (`lists` as an array).
- KML 2.2: a Placemark for each place, all text XML-escaped.
- HTML report: title, date generated, selection summary (circle centre/radius in km, or "custom lasso"), then one card per place. Inline CSS, a CSP meta tag, no external requests, `@media print` rules.
- File names: `maps-plus-<listnames-or-selection>-<YYYY-MM-DD>.<ext>` (up to three list names, otherwise "selection").
- Downloads use an `<a download>` blob link, **only when the user clicks an export button**, so the `downloads` permission isn't needed.
- Map links: `?cid=` when known, otherwise `search/?api=1&query=lat,lng`.

## Code conventions

- Small pure functions for parsing, projection, geometry, and protobuf building. All of them get unit tests with fixtures.
- Only UI modules touch the DOM. Only the background worker makes network requests.
- User-facing errors are short and specific. Log details with a `[maps-plus:<feature>]` prefix (`shared/log.ts`), and only when debug logging is turned on in the options page.
- Commit style: Conventional Commits (`feat(saved-lasso): …`, `fix(pano-date): …`).

## Publishing notes

- The extension name must not suggest it's made by Google: "Maps Plus — for Google Maps", with our own icon (`docs/icon.svg`: a dashed lasso, a pin, and a plus, on green; no Google iconography).
- README must include: the feature list, the privacy statement (no data collection), the fact that it relies on undocumented Google endpoints that may break, credit to itisem/emily for the date-resolving technique, and a note that use is subject to Google's Terms of Service.
- Chrome Web Store privacy questionnaire: "does not collect or transmit user data." The policy text is in `PRIVACY.md`.
